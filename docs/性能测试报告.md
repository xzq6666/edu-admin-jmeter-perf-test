# 教务管理系统接口性能测试报告

| 项 | 内容 |
| --- | --- |
| 被测系统 | 教务管理系统（Spring Boot 后端，`http://localhost:8082/api`） |
| 测试类型 | 负载测试（并发梯度递增，定位性能拐点与瓶颈） |
| 压测工具 | Apache JMeter 5.6.3（非 GUI 模式） |
| 执行日期 | 2026-11-08 |
| 结论摘要 | 登录接口在 **10 并发即达吞吐天花板（约 7.4 TPS）**，100 并发出现 13.54% 超时失败；查询接口 10 并发 164 TPS 表现正常，50 并发后吞吐下滑。瓶颈为 **BCrypt 密码校验 CPU 争用** 与 **MyBatis 同步控制台日志 I/O**，非数据库容量问题。 |

---

## 一、测试目标

1. 摸清核心接口在不同并发下的吞吐（TPS）、响应时间分位（P50/P90/P95/P99）与错误率；
2. 找到系统的性能拐点，判断在多少并发下开始劣化、在多少并发下不可用；
3. 对劣化现象给出可验证的根因定位，而不是停留在"变慢了"的表象；
4. 输出可复现的压测脚本与结论，便于优化后回归对比。

## 二、测试环境

| 项 | 配置 |
| --- | --- |
| 操作系统 | Windows 11 |
| CPU / 内存 | 4 逻辑核（JMeter 日志 `Available Processors =4`）/ 16 GB |
| JDK | OpenJDK 17.0.15 LTS |
| 后端 | Spring Boot（内嵌 Tomcat），上下文路径 `/api`，端口 8082 |
| 数据库 | MySQL 8（`localhost:3306/edu_admin`），连接池 Druid `max-active: 20`、`initial-size: 5`、`max-wait: 60000ms` |
| 缓存 | Redis 7（`localhost:6379` db0），Jedis 连接池 `max-active: 8` |
| 压测工具 | JMeter 5.6.3，堆上限 512 MB |
| 压测机 | **与被测服务同机**（单机压测） |

> **局限声明**：JMeter 与被测后端运行在同一台 4 核机器上，压测进程本身会争抢 CPU，因此绝对 TPS 数值偏低，不能等同于生产容量。本报告的数据用于**同一环境下的横向对比与瓶颈定位**，结论对"哪个环节先撑不住"有效，对"生产能扛多少并发"不作承诺。这一条必须在引用数据时一并说明。

## 三、测试模型

### 3.1 场景设计

| 场景 | 接口 | 业务含义 | 选它的理由 |
| --- | --- | --- | --- |
| 场景一：登录 | `POST /api/auth/login` | 账号密码登录，返回 JWT | 全站入口，且含 BCrypt 哈希运算，是典型的 CPU 密集型接口 |
| 场景二：核心查询 | `GET /api/admin/students`、`GET /api/admin/courses`、`GET /api/schedule/rooms` | 学生分页列表、课程分页列表、教室字典 | 后台高频读操作，覆盖分页查询与字典查询两种形态 |

### 3.2 参数与执行策略

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 并发梯度 | 10 / 50 / 100 线程 | 三级递增，观察吞吐拐点 |
| 爬坡时间（Ramp-up） | 5 s | 避免瞬时冲击掩盖真实曲线 |
| 单轮持续时长 | 30 s | 保证稳态样本量，同时控制测试总时长 |
| 循环方式 | 调度器控制（按时间循环） | 线程在 30 s 内持续迭代 |
| 超时设置 | 连接 5 s / 响应 15 s | 15 s 作为"用户可忍受上限"，超过即记失败 |
| 断言 | 响应体含 `"code":200` | 避免只看 HTTP 200 而漏掉业务失败 |
| 执行方式 | `jmeter -n`（非 GUI）+ `-e -o` 生成 HTML 报告 | 排除 GUI 自身开销对结果的干扰 |

### 3.3 请求内容

- 登录：`{"username":"admin","password":"admin123"}`，`Content-Type: application/json`；
- 查询：携带 `Authorization: Bearer <token>`，token 由压测前独立登录取得并通过 `-Jtoken` 注入，**保证查询场景的耗时不含登录成本**；
- 查询参数固定为 `page=1&size=10` 与 `semester=2026-2027-1`，gzip 关闭，连接复用（Keep-Alive）开启。

## 四、测试结果

### 4.1 登录接口 `POST /api/auth/login`

| 并发 | 样本数 | 吞吐 TPS | 平均 (ms) | P50 (ms) | P90 (ms) | P95 (ms) | P99 (ms) | 错误率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 244 | **7.38** | 1245 | 863 | 1373 | 4018 | 10682 | 0% |
| 50 | 221 | **6.92** | 6546 | 7402 | 10763 | 11569 | 13432 | 0% |
| 100 | 384 | **12.01** | 7600 | 6107 | 15006 | 15010 | 15014 | **13.54%** |

**读数要点**

1. **10 并发就已达天花板**：TPS 7.38，此时平均响应已 1.2 s、P95 4 s。加并发不再提升吞吐。
2. **50 并发吞吐反而下降（7.38 → 6.92）**：这是典型的**过饱和信号**——线程数超过系统处理能力后，上下文切换与锁竞争的开销吃掉了本可用于计算的 CPU，有效吞吐不升反降，同时 P95 恶化到 11.6 s。
3. **100 并发进入不可用区**：P90/P95/P99 全部顶在 15 s（正好等于设定的响应超时），13.54% 的请求因超时被判失败；名义 TPS 12.01 是被超时请求快速释放连接"抬"上去的，**不代表处理能力提升**，实际成功吞吐约为 12.01 × 86.46% ≈ 10.4 TPS，且延迟已不可接受。

### 4.2 核心查询接口

| 并发 | 样本数 | 吞吐 TPS | 平均 (ms) | P50 (ms) | P90 (ms) | P95 (ms) | P99 (ms) | 错误率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 4892 | **164.49** | 56.3 | 53 | 103 | 125 | 220 | 0% |
| 50 | 2592 | **86.36** | 533.9 | 389 | 1201 | 1618 | 2271 | 0% |
| 100 | 2233 | **73.80** | 1249.0 | 1080 | 2576 | 3086 | 3995 | 0% |

**读数要点**

1. **10 并发表现健康**：164 TPS、平均 56 ms、P95 125 ms，说明单请求本身不慢，SQL 与索引没有明显问题。
2. **50 并发吞吐降至一半（164 → 86）**：平均响应从 56 ms 升到 534 ms，放大约 9.5 倍；P95 从 125 ms 升到 1618 ms，放大约 13 倍。吞吐降、延迟升，是**资源排队**的典型特征，而不是单条 SQL 变慢。
3. **100 并发继续劣化但无错误**：TPS 74、平均 1.25 s、P95 3.1 s，尚未触达 15 s 超时线，所以错误率为 0，但延迟已明显超出体验阈值。

### 4.3 两个场景的对比结论

同一环境下，**登录 7.4 TPS vs 查询 164 TPS，相差 22 倍**。两者共用同一个 Tomcat、同一个 JVM、同一台机器，唯一显著差异是登录多了"密码哈希校验"这一步。这个数量级差异直接把矛头指向密码哈希，而不是 JVM、网络或数据库。

## 五、瓶颈定位

### 瓶颈一（首要）：BCrypt 密码校验吃满 CPU

**证据链**

1. 代码证据：`SecurityConfig.java:58` 使用 `new BCryptPasswordEncoder()`，未指定 strength，采用**默认强度 10**（2^10 = 1024 轮迭代）。这是一次刻意的、计算密集的哈希运算。
2. 数据证据：单次登录最小耗时 343 ms、平均 1.2 s（10 并发）；而纯查询最小 2 ms、平均 56 ms。差值几乎全部来自哈希计算与登录链路。
3. 曲线证据：并发从 10 加到 50，TPS 不升反降——这是 CPU 已饱和的标志，加并发只会增加排队与切换开销。

**登录链路拆解**（每个请求都要走一遍）：

```
请求 → Redis 查登录失败计数/锁定标记 → MySQL 查 sys_user
     → BCrypt 比对密码（CPU 主力开销） → 生成 JWT
     → 写 Redis 当前 token（单端在线策略，覆盖旧 token）
```

其中 BCrypt 是唯一随并发呈线性膨胀的 CPU 开销项；Redis 每请求多次往返、Jedis 池上限仅 8 个连接，在并发升高后也会成为二次排队点。

### 瓶颈二：MyBatis 同步控制台日志拖慢查询

**证据**

`application.yml` 中同时开启了：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # 每条 SQL 直接打印到控制台
logging:
  level:
    com.edu.admin: DEBUG
    com.baomidou.mybatisplus: DEBUG
```

`StdOutImpl` 是**同步写标准输出**，不是异步日志。每次查询都要把 SQL、参数、结果集行数打印到控制台；在 Windows 控制台 + IDE 输出窗口下，这种 I/O 会直接阻塞工作线程。

**数据对应**：查询接口 10 并发 164 TPS 说明单语句本身够快，但 50 并发就掉到 86 TPS 且**零错误**——如果是 DB 连接不够，通常伴随获取连接超时和错误；这里是"变慢但都成功"，更符合"线程在等 I/O"的特征。

### 瓶颈三：Druid 连接池上限 20

**证据**：`application-dev.yml` → `druid.max-active: 20`、`max-wait: 60000`。

50 与 100 并发时，同时在跑的数据库请求远超 20，多出的线程在池上排队等连接，`max-wait` 给到 60 s 意味着它们会**静默地等**而不是快速失败——表现为延迟平滑地上涨（534 ms → 1249 ms），错误率为 0。这与实测曲线完全吻合。

### 瓶颈四：Redis Jedis 连接池上限 8

**证据**：`application-dev.yml` → `spring.data.redis.jedis.pool.max-active: 8`。

登录链路每请求至少 2–3 次 Redis 操作（失败计数读取、token 写入、可能的过期设置），8 个连接在 50/100 并发下成为明确的串行点。它虽不是主因，但会在 BCrypt 优化后浮上来成为下一个瓶颈。

## 六、优化建议

按"投入产出比"排序，每条都给出预期收益与验证方式。

| 优先级 | 措施 | 依据 | 预期收益 | 验证方式 |
| --- | --- | --- | --- | --- |
| P0 | 登录结果短时缓存：同一账号在 N 秒（如 5 s）内重复登录直接返回上一次 token，不再重复哈希 | 压测中 100% 请求都是 `admin/admin123`，真实业务里同一用户重复登录同样常见 | 登录 TPS 可提升一个数量级（取决于命中率） | 保持 100 并发重跑，观察 TPS 与 P95 |
| P0 | 评估 BCrypt strength：从默认 10 降到 8（约 4 倍速度提升），或改用 Argon2 并按硬件调参 | 单次哈希 300 ms+ 在 4 核上明显偏重 | 登录 TPS 约 7.4 → 25~30 | 单接口基准测试对比 |
| P1 | 关闭 `StdOutImpl`，改用 SLF4J 异步 Appender，生产日志级别降到 INFO/WARN | 每条 SQL 同步写控制台 | 查询 TPS 有望从 164 提升到 300+ | 50/100 并发重跑对比 |
| P1 | Druid `max-active` 从 20 提到 50，并核对 MySQL `max_connections` 与慢查询 | 并发超过 20 后排队 | 50/100 并发下延迟增长显著放缓 | 观察 P95 与连接池等待时间 |
| P2 | Jedis 池 `max-active` 从 8 提到 32，或切换 Lettuce（基于 Netty，异步非阻塞） | 登录链路 Redis 往返密集 | 缓解 BCrypt 优化后的次生瓶颈 | 压测中监控池等待 |
| P2 | 登录接口按 IP / 账号维度限流（如 20 次/分钟），超出返回 429 | 登录是最易被刷的接口 | 保护后端不被恶意并发打穿 | 用本仓库脚本验证限流生效 |
| P3 | Tomcat `max-threads`、`accept-count` 按实测拐点调整；引入网关层统一限流 | 当前用默认值，未针对业务调优 | 避免线程堆积导致的内存与切换开销 | 阶梯压测找新的拐点 |

> 建议按 P0 → P1 顺序做，每改一项就用本仓库脚本重跑同一梯度，把优化前后的 `summary.csv` 放在一起对比——**有前后对比数据的性能报告，才是能拿去面试讲的东西**。

## 七、结论

1. 系统的**读能力明显强于写/鉴权能力**：查询 164 TPS 可用于正常业务，登录 7.4 TPS 是短板。
2. 登录接口的瓶颈是**算法层面的故意开销**（BCrypt）叠加**连接池上限**，不是代码写得烂，也不是数据库不行；优化方向明确且成本低。
3. 查询接口在 10 并发下健康，50 并发即腰斩，根因指向**同步控制台日志 I/O** + **连接池 20 的上限**，属于配置问题，改配置即可见效。
4. 100 并发是当前配置下登录接口的**不可用边界**（13.54% 超时），可作为容量红线。

## 八、复现步骤

```powershell
# 1. 确认被测后端可访问
#    POST http://localhost:8082/api/auth/login 应返回 {"code":200,...,"data":{"token":"..."}}

# 2. 一键执行全部梯度（默认 10/50/100 并发、30 秒、爬坡 5 秒）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\run_all.ps1

# 3. 自定义梯度
powershell -File scripts\run_all.ps1 -Threads "20,60,120" -Duration 60 -Ramp 10

# 4. 查看产物
#    results\summary.csv              各轮指标汇总
#    results\html\<场景>_<并发>\index.html   JMeter 官方 HTML 报告（含 TPS 曲线、响应时间分布、百分位表）
```

前置条件：JMeter 5.6.3 与 JDK 17 已安装；脚本默认从 `D:\apache-jmeter-5.6.3` 读取 JMeter，路径不同时用 `-JmeterHome` 指定。

## 九、说明与免责

- 本报告为**单机压测**，压测器与被测服务共享 CPU，绝对数值低于独立压测机的结果；所有结论用于同环境横向对比与瓶颈定位。
- 压测会对 `admin` 账号反复登录，造成 Redis 中该账号 token 频繁覆盖（单端在线策略），不影响业务正确性，但压测期间其他会话可能被顶下线。
- 测试环境为本地开发配置（含 DEBUG 日志、默认连接池大小），与生产配置存在差异，优化前后对比须在同一配置基线下进行。
